# Documentation Governance System

Date: 2026-04-30

## Purpose

This system keeps the Game Design Knowledgebase maintainable as documentation grows.

The goal is not to stop useful documentation. The goal is to prevent every new need from becoming another permanent first-use file.

## Governance Principles

- Every document must have a target user.
- Every document must have a lifecycle state.
- Every document must link to a parent or hub.
- First-use files must stay few.
- Governance, audit, benchmark, schema, and generated files must not compete with first-use files.
- Generated files must be regenerated by tools, not edited manually.
- Source governance rules must not be weakened for usability.

## Lifecycle States

| State | Meaning | First-use visible? |
|---|---|---|
| active_first_use | shortest path for normal users | yes |
| active_use_case | task-specific user journey or prompt route | yes, after route selection |
| active_runtime | AI behavior, context, prompt, or runtime rules | only when using AI |
| active_reference | deeper explanation or framework reference | no by default |
| active_governance | policy, audit, validation, or maintenance control | no for normal users |
| generated | tool-created report or export | no manual editing |
| legacy | retained historical or migrated material | no |
| deprecated | explicitly inactive material | no |
| archive_candidate | duplicate, stale, or superseded material awaiting review | no |

## Required Metadata For New Docs

New documentation should answer:

- Purpose: what problem does this file solve?
- Target user: human user, AI agent, maintainer, auditor, or source reviewer.
- Entrypoint role: first-use, use-case, runtime, reference, governance, generated, legacy, or deprecated.
- Linked parent: which hub or index points to it.
- Update owner: who keeps it current.
- Source/confidence policy: whether the file may discuss evidence, claims, or confidence.
- Deprecation condition: when the file should be retired or merged.
- Surface level: Level 0 through Level 6 from `REPO_SURFACE_LEVELS.md`.

## Bloat Control Rules

- Do not create a new root file if an existing hub can absorb the update.
- Do not create another first-use file unless one existing first-use file is demoted or clearly stays subordinate.
- Do not duplicate a prompt in multiple places; link to the canonical prompt file.
- Do not duplicate runtime rules; link to the canonical runtime or source-safety file.
- Do not create synthetic examples without the explicit synthetic labels already used by the worked examples.
- Do not add evidence intake docs to the first-use layer unless the user is doing evidence work.
- Do not add benchmark internals to normal user navigation.

## Maintenance Cadence

| Frequency | Action |
|---|---|
| Every prompt phase | append `report.md`; update current-state docs only if truth changed |
| Every usability phase | check first-use top 10 and use-case hub |
| Every evidence phase | check source governance, evidence status, and confidence language |
| Every benchmark phase | keep benchmark status honest; do not fabricate outputs |
| Monthly or milestone | run duplication and rot-risk review |

## Enforcement

Documentation governance is enforced by review checklists, maintainers, and validation where rules are machine-checkable.

Machine-checkable gates include:

- validation pass;
- source governance pass;
- required first-use files exist;
- required prompt/context-pack files exist;
- private and archive source files are not committed;
- generated exports are current.

Human-review gates include:

- document purpose is clear;
- document has an owner;
- document belongs to the right layer;
- document does not create first-use overload;
- document does not weaken source/confidence boundaries.
